# 10 · YSM 桌宠（透明背景窗口）

> 状态：**可运行**。`python scripts/run_pet.py` 直接起桌宠。
> 渲染走 C++ 光栅（`native/raster.dll`），稳态 **~18 ms/帧 ≈ 55 fps**。

---

## 1. 一句话定位

把 `.ysm` 模型渲染在一个**无边框、置顶、逐像素透明**的窗口里，悬在桌面上，
带呼吸 / 摆头 / 眨眼待机动画，可拖拽、可缩放、可鼠标穿透、可切表情。

## 2. 运行

```bash
# 需要 C++ 光栅：先编一次（已编好可跳过）
python scripts/build_native.py

# 启动（默认亚托莉，1.5 倍，30fps）
python scripts/run_pet.py --scale 1.5 --fps 30

# 不开窗口，只渲几帧存 PNG 自检
python scripts/run_pet.py --smoke --frames 3

# 换模型
python scripts/run_pet.py --model 爱恩.伊瑞丝.卡列尼娜.bin
```

**三种方式打开设置面板**：右键菜单「设置…」/ **双击桌宠** / **单击托盘图标**。

**设置面板**（`SettingsPanel`）分组：

| 分组 | 可调参数 |
|---|---|
| 显示 | **光影（默认关闭）**、自动旋转 + 转速 °/s、缩放 0.75~3x、目标帧率 5~120 |
| 朝向 | 水平 yaw −180~180、俯仰 pitch −60~60、复位（回到 28/10） |
| 动画 | 待机动画（呼吸 / 摆头 / 眨眼）开关 |
| 表情 | 启用表情开关 + **5 个表情轮盘**（脸/眉/眼/嘴17项/眨眼） |
| 窗口 | 置顶、鼠标穿透 |
| 底部 | 关闭面板、**退出桌宠**（红色，即关闭键） |

**表情轮盘** `ExpressionWheel`：选项沿圆周排成扇形，中心写槽位名，点扇区即选中，
选中扇区高亮蓝色。嘴有 17 个选项，用轮盘比一排按钮紧凑得多。
表情本质是「显隐」（`scale=(0,0,0)` 隐藏未选中选项），叠加在待机动画之上。

**左键拖拽**移动位置。

## 3. 文件

| 文件 | 作用 |
|---|---|
| `src/pet/loader.py` | 读 `.ysm` → 骨骼树 + 贴图 + 待隐藏骨骼 |
| `src/pet/fastrender.py` | 向量化 FK + 批量变换 + C++ 光栅 → 透明 RGBA |
| `src/pet/petapp.py` | `IdleAnimator`（待机动画）、`RenderThread`、`PetWindow` |
| `scripts/run_pet.py` | 入口（含 `--smoke` 自检） |
| `scripts/build_native.py` | 编译 `native/raster.cpp` → `raster.dll` 并做 ctypes 冒烟 |
| `scripts/verify_cpp.py` | **一致性验证**：C++ 全管线 vs Python 参考，逐像素对比 |
| `scripts/make_python_def.py` | 从 `python313.dll` 导出表生成 `libpython313.a`（给 MinGW 用） |

管线（与需求一致）：**读 ysm → 解贴图 → 建骨骼树 → 骨骼矩阵驱动渲染**。

## 4. 关键技术事实（踩过的坑）

### 4.1 内嵌贴图是裸 RGBA，不是 PNG
`亚托莉.ysm` 里 `textures['ATRI']` 是 `256*256*4 = 262144` 字节的**裸 RGBA**，
与 `outputs/step4/tex.png` 逐字节相同。`loader._decode_image()` 按
PNG 魔数 / `w*h*4` / 正方形猜测三级判断。
另外 `properties.default_texture` 写的是 `"default"`，但字典里根本没有这个键，
所以兜底取第一个非 `/ARROW\` 的贴图。

### 4.2 相机目标必须用 pb 空间包围盒中心（重要 bug 修复）
顶点已经 `Vp = (Vw - ctr) @ P_MAT.T` 居中了，若相机目标再传 `P_MAT @ ctr`
就是**双重偏移**——模型被推到画面右下方且被放大 24%。
**此前所有 fast 渲染图（含 `outputs/step6/fast_rgba.png`）都受此影响。**
现在 `FastRenderer` 用 `self.pctr`（居中后顶点在 pb 空间的包围盒中心）做目标，
模型完整且居中。

### 4.3 pybind11 在本机不可用（结论，别再试）
| 产物 | 结果 |
|---|---|
| 纯 C 扩展（链 python313） | ✅ `add(3,4)=7.0` |
| C++ 用了 `std::string/vector` | ❌ WinError **1114** |
| pybind11 2.11.1 / 2.13.6 | ❌ WinError **1114** |

根因不是 pybind11：**MinGW(TDM 4.9.2) 的 libstdc++ 只要进入「DLL 形态」，
在 DllMain 里做 C++ 运行时初始化就崩**。静态链/动态链/有无全局静态对象都一样。
`raster.dll` 能用是因为它虽然叫 `.cpp`，实际是纯 C 代码，没碰 libstdc++。

**工程约束由此确定：`native/` 下的核心一律纯 C ABI、禁用 `std::` 容器。**
这对最终"单一 exe"毫无损失——`-static` 对 `.exe` 是好的（exe 自己跑 CRT
初始化，不走 DllMain），坏的只有"往 Python 进程里塞 C++ .pyd"这一条路。

配套工具：`scripts/make_python_def.py`——Dev-C++ 没有 gendef，该脚本直接解析
`python313.dll` 的 PE 导出表（1656 个符号），产出 `.def` 再用 `dlltool`
生成 MinGW 可用的 `libpython313.a`。这是让纯 C 扩展能链上 Python 的关键。

### 4.4 明暗默认关闭（平涂）
用户反馈半球光效果依然不自然（方块模型法线只有 6 个主方向，任何方向光都会
出现「某一侧整体发暗」的硬跳变）。**现在默认平涂**：`FastRenderer.lighting = False`，
`shade` 全 1，直接输出贴图原色。需要时再开：

    python scripts/run_pet.py --lighting      # 命令行
    右键菜单 → 光影                            # 运行时切换

`--lighting` 用的是下面的半球光方案（保留但未启用）。

### 4.4b 光照：旧方向光导致「半数面死黑」（已改为半球光）
旧光向 `[0.45,-0.60,0.66]`（pb 空间）是**上方偏「后」**，实测后果：
- 脸（正面 -Z）只有 shade 0.753，最违和
- `p50 = 0.551`：**超过一半的面被 clamp 到同一个最暗值**，左/下/后三个方向 shade 完全相同
- 明暗是「要么亮要么死黑」的二值跳变

现改为**半球环境光 + 上前左主光**（`fastrender.py` 顶部 `_LIGHT`/`_AMB`）：

    shade = 0.60 + 0.22*(0.5+0.5*n_up) + 0.18*max(dot(n,L), 0)
    L = normalize([0.50, 0.40, 0.77])   # pb 空间：+X前 +Y左 +Z上

实测分布：上 0.958 / 前(脸) 0.800 / 左 0.782 / 右·后 0.710 / 下 0.600，
唯一取值 294 个，最暗面占比 14.5%。脸亮、顶面最亮、底部柔和偏暗，不死黑。

### 4.5 透明窗口的坑（Windows / Qt6）
`setAttribute(WA_TranslucentBackground, True)` 会让 Qt 启用分层窗口做逐像素 alpha，
**它会自动同时打开 `WA_NoSystemBackground`**。若再手动 `setAttribute(WA_NoSystemBackground, False)`
就把透明背景关掉了 → 窗口出现不透明底色。
`paintEvent` 里必须先用 `CompositionMode_Source` 把整块（含 alpha）清成透明再画，
否则上一帧残留会叠在模型周围。

### 4.7 抗锯齿（SSAA，默认 2x）
软光栅本身没有 MSAA，最近邻采样 + 硬边三角形导致轮廓锯齿明显。方案是 **SSAA**：
以 `ssaa` 倍分辨率渲染，再下采样回目标尺寸。

* **alpha 取算术平均** → 轮廓从 0/255 二值变成软边（这是消锯齿的关键，
  对透明窗口尤其重要）
* **RGB 按 alpha 加权平均** → 半覆盖像素不会被未覆盖处的 0 值拉黑

**下采样放 C++**（`native/raster.cpp :: downsample_rgba`）：Python 侧做同样的事
要先把 `300x450x4` 转成 float32（2.2 MB）再按轴求和，产生好几个同等大小的临时
数组；C++ 一遍循环直接出结果，零临时分配。实测 150x225：

| ssaa | numpy 下采样 | C++ 下采样 | 软边像素 | alpha 唯一值 |
|---|---|---|---|---|
| 1 | 17.4 ms | 15.0 ms | 0 | 2（纯二值） |
| 2 | 43.5 ms | **22.1 ms (45 fps)** | 355 | 5 |
| 3 | 64.6 ms | **28.1 ms (36 fps)** | 501 | 10 |

C++ 与 numpy 实现逐像素最大差 1（舍入）。设置面板「显示 → 抗锯齿」可选 关/2x/3x。

### 4.8 共面 z 打平：已改为**按三角形序号确定性取舍**
YSM 方块模型在 1/16 网格上建模，大量面精确共面，z 差只有 1 ULP（实测
`|zA-zB|` p50=0，max=2.22e-16）。如果只用 `z < ZB`，胜者就由浮点噪声和
**遍历顺序**共同决定 —— 这是之前 Python 参考实现与 C++ 全管线"看起来处处对
不上"的真正原因：

> 同一批三角形数据仅仅是**换个排列顺序**（SoA ↔ AoS），就有
> **13558 个像素不同、平均差 16.8**。光照模式下尤为明显，因为共面的两个面
> 明暗不同，顺序一变颜色就变。

修法（`raster_faces`）：加一张 `ZI` 序号表，当新来的 z 与已记录的 z 在 `1e-12`
内视为相等时，**取序号更小者**。这样结果与遍历顺序无关，两条路径可逐像素对齐。
配套地在 `fastrender.py::_render_raw` 里把四边形拆三角改成 **AoS 布局**
（面0三角A、面0三角B、面1三角A…），与 C++ 完全一致。

### 4.9 C++ 全管线一致性验证（`scripts/verify_cpp.py`）
把 FK 之后的每一步（顶点变换 → 法线 → 背面剔除 → 投影 → 拆三角 → 光栅 →
SSAA 下采样）搬进 C++（`ysm_new` / `ysm_render` / `ysm_free`），Python 侧只
留 FK + pybullet 相机矩阵。中间结果（`Vh`/`matmul` 中间量/`clip`/三角数组）
**全部不再分配**。

验证方式是同一姿态、同一相机下逐像素对比「C++ 全管线」与「Python 参考实现」：

| ssaa | lighting | 覆盖像素 | max 差 | mean 差 | 不同像素 |
|---|---|---|---|---|---|
| 1 | 平涂 | 14398 | 0 | 0.0000 | **0** |
| 1 | 光影 | 14398 | 0 | 0.0000 | **0** |
| 2 | 平涂 | 14663 | 0 | 0.0000 | **0** |
| 2 | 光影 | 14677 | 0 | 0.0000 | **0** |
| 3 | 平涂 | 14761 | 0 | 0.0000 | **0** |
| 3 | 光影 | 14780 | 0 | 0.0000 | **0** |

（3 帧 × 各档位共 18 组，全部为 0。）

调试期间留下的 `ysm_dump_last()` 保留在 DLL 里 —— 它能把某次 `ysm_render`
**实际**写进光栅器的 `P/U/S` 导出给 Python，是这回定位顺序问题的关键工具，
以后怀疑"C++ 画的和 Python 不一样"时可直接复用。

## 7. 取景 / 窗口 / 抗锯齿（2026-10-05 修订）

### 7.1 窗口尺寸按模型算，不再硬编码

旧实现 `BASE_W, BASE_H = 150, 225`。问题：150:225 = 0.667，而模型渲染出来的
人物只有 ~0.44 的宽高比 → 窗口比人宽一圈，两侧大片空白，看着"人窄窗口宽"。

**新规则**（`PetWindow._size`）：

```
H = 225 * scale                      # 高度仍按基准
W = H * 人物渲染宽高比 * FIG_W_PAD    # 宽度跟着模型收紧（PAD=1.25）
```

**为什么不能用一个"人物占窗高 X%"来算**：人物像素尺寸与窗口尺寸**成正比**
（同 zoom 下 200x300→75x170、400x600→149x339，比例恒 0.44）。也就是说
"人物占窗高"是个**常数**、完全由 zoom 决定，跟窗口怎么开无关。所以窗口
只负责"形状"（宽:高），"占比"交给 zoom。

实测：**150x225（占高 57%）→ 121x225（占高 73%）**，窗口贴合模型。

### 7.2 渲染宽高比用 `measure_ratio()`，不用静态包围盒

`FastRenderer.aspect` 是**静态顶点**在 pb 空间的跨度，把 A-pose 张开的双臂
也算进去了（亚托莉 0.80），比实际渲染（0.44）大近一倍，用它定窗口会左右各空
1/4。`measure_ratio()` 离屏渲 24 帧、取 alpha>0 包围盒的宽高比**中位数**并缓存，
才是真实观感。

### 7.3 zoom 与"人物占窗高"的对应（实测）

| zoom | 人物占窗高 | 用途 |
|---|---|---|
| 1.20 | 85% | 顶到边 |
| 1.30 | 78% | 偏大 |
| **1.38** | **73%** | **当前默认** |
| 1.50 | 67% | |
| 1.75 | 57% | 旧默认（偏小） |
| 2.00 | 49% | 太小 |

`zoom` 语义：`dist = radius / tan(fov/2) * zoom` —— **越大 → 相机越远 → 人越小**。

### 7.4 抗锯齿（SSAA）现状

**功能正常**：`ss=1` 中间 alpha 像素 0（硬边）；`ss=2`→554；`ss=3`→728（软边）。
链路：`ysm_render` 以 `bw = W*ss` 的分辨率光栅 → `downsample_rgba` 求平均。
放大脸部对比可见 ss=3 的刘海/轮廓明显平滑。

**为什么有时"看着没效果"**：SSAA 的软化宽度是**亚像素**级的。当窗口很大
（如旧 `scale=2.0` → 300x450）时，软化只占一两个像素，肉眼就被稀释了；
窗口收紧后同一档位观感明显得多。

### 7.5 设置面板的坑（两条）

1. **必须带 `Qt.Window`**。只写 `Qt.WindowStaysOnTopHint` 时 widget 没有
   Window 位，Qt 会把它当**桌宠的子部件** —— 点面板的 × 会**连带关掉桌宠**。
2. **尺寸要跟 `sizeHint()`**。面板内容 `sizeHint` 是 798×518（宽扁），
   若硬 `resize(560,560)` 压成窄高条，控件会换行、看着"又窄又长"。

### 7.6 转向：只转头，不转眼

`GazeTracker.to_anim()` **只写头骨骼（`AllHead`）一条 rot**，眼骨骼完全不写。

理由：MC 皮肤的眼睛是**画在脸上的贴图色块**，不是可动部件。去转眼骨骼只会让
眼球块/眉毛/眼睑跟着位移，看着像"眼珠滑出眼窝"；而原版的行为本来就是
**整个头转过去**，眼睛始终长在脸上跟着头走。

`eye_driven` 属性恒返回空元组，仅为兼容旧调用保留。
`eye_share` 参数已**删除**（见 §9.3：它会在中位补偿上再乘一次系数，把头转坏）。

> 曾经的两次错误（都已修）：
> 1. 用 `"eye" in n.lower()` 把 24 个后代各写一遍 rot →
>    `pose_matrices` 父子累积导致旋转叠加 2~6 层、五官错位；
> 2. 改成"只驱动眼骨骼本身" → 五官不叠加了，但眼睛仍在转，
>    不符合"眼睛只是算方向用的"这一要求。
>
> 3. （2026-10-05 二轮）又用 `k = 1 - eye_share*0.5` 去"削弱"头部转角 ——
>    眼球不转之后这一份没有去处，纯粹让头转不够，已删。

## 8. 2026-10-05 二轮：窗口按全动画包围盒 / 设置面板分页 / 视线绑定 / 常驻

### 8.1 窗口尺寸 = **所有动作渲染后的全局包围盒**

需求原话："应该按照桌宠目前渲染最大 y 值和 x 值做窗口绑定，因为不同动作或
朝向的 xy 比例并非一成不变。"

**实测各动画的宽高比差得极大**（亚托莉，56 个动画）：

| 动画 | 宽高比 | 备注 |
|---|---|---|
| 跳跃/攻击/extra1 | 0.42~0.43 | 最窄（立姿） |
| 行走 | 0.57~0.59 | |
| swim / extra11 | 1.77~2.06 | 最宽（横向趴伏） |

**踩过的大坑（返回 0.6667 的真相）**：
一开始直接在**目标窗口尺寸**（140×210）上遍历动画量包围盒 → 宽动作一渲染就
顶到画面左右边缘 → 包围盒恒等于整个画幅 → "所有动作的并集"必然 = 画幅 →
比例永远 = 140/210 = 0.6667。**这是在量自己的取景框**。

修法：用一块**方形大方幅**（默认 260×260，ssaa=1）当探针渲染，再把像素
包围盒换算回 pb 空间：

```
span_v = 2*dist*tan(fov/2)
width_pb  = (gx1-gx0+1)/W * span_h
height_pb = (gy1-gy0+1)/H * span_v
ratio = width_pb / height_pb      # 与探针尺寸无关
```

验证尺寸无关性：260×260 → 0.8692，400×200 → 0.8650（一致）；缓存命中后
**2.24s → 0.011s**。

窗口公式：`W = H * ratio * FIG_W_PAD`，`H = BASE_H * scale`。
`FIG_W_PAD` 从 1.45 收到 **1.25**（比例本身已含最宽动作）。亚托莉：
**369×340**，最宽的 extra11 占宽 62%、立姿 25~40%，任何动作不裁切。

### 8.2 比例磁盘缓存

`fastrender.py` 新增模块级 `_load_ratio_cache` / `_save_ratio_cache`，
存到 `%LOCALAPPDATA%\YSMPet\ratio_cache.json`（JSON，人类可读，原子写）。
键 = 模型路径；**存的是相对基准 pctr 的偏移**（不是绝对值，因为 pctr 依赖
radius/zoom 会随窗口重算）。`_ratio_base_pctr` 在 `measure_ratio` 里记原值。

### 8.3 设置面板：左导航 + 分页

原两列堆叠 → 内容一多就拉长（"过窄过长"）。改为：

* 左侧 `QListWidget` 导航（显示/朝向/动画/视线/窗口），右侧 `QStackedWidget`；

### 8.5 视线绑定：相机方位补偿（⚠️ 此版推导已被 §9.3 取代）

**这是"视线跟踪绑定错误"的第一版正解。** 头骨骼 rot 施加在**模型局部空间**，
而相机是斜看的（默认 yaw=28° 的 3/4 侧视）。当时的做法是把屏幕方向反解到模型
世界空间：

```
turn  = nx*cos(cam_yaw)          # 屏幕向右 → 绕竖直轴的转向分量
yaw   = turn * max_yaw
pitch = ny * max_pitch
```

`GazeTracker` 新增 `set_camera(yaw, pitch)`，由 `PetWindow._poll_gaze` 每帧
喂入 `thread.yaw/pitch`（支持自动旋转时相机在动）。

⚠️ **这一版有两个问题，已在 §9.3 修掉**：
1. `cos(cam_yaw)` 只是个凭感觉的缩放，且**没有中位补偿** —— 人物正面本来就
   离镜头 62°，所以"光标在正中"时头是偏的，"光标在右"最多把头顶到正脸、
   "光标在左"直接扭到后脑勺，用户看着就是"绑定反了"。
2. 推导里"屏幕右 = 模型 (cos cy, -sin cy)"其实把 pybullet 的 yaw 约定猜错了。

**外部参考佐证**（YSM 官方 Molang 约定，见于 MC 百科"YSM 常用 Molang"）：
* 眼部追踪 → 部位"瞳孔/眼球"，关键帧是**位置**（`ysm.head_yaw/180` 位移），
  **不是旋转**；
* 头部锁定 → 部位"头部"，关键帧是**旋转**（`math.clamp(ysm.head_yaw,-60,60)`）。

即"头旋转、瞳孔位移"，与我们的"只转头、眼骨骼不动"完全一致 —— 眼睛是
贴图不是可动件，这也解释了为什么之前转眼骨骼会"眼珠滑出眼窝"。

## 9. 2026-10-05 三轮：并行动画层 / 比例缓存修正 / 视线正面补偿

### 9.1 动态部件被"固定"→ 补上并行层（`ResidentPlayer`）

**根因：完全没有实现原版 YSM 的 `pre_parallel*` / `parallel*` 层。**

`.ysm` 的 `main` 组里有两类特殊动画：

| 名字 | 作用时机（原版） |
|---|---|
| `pre_parallel0..N` | 主体动画**之前**（基础校正层） |
| `parallel0..N` | 主体动画**之后**（覆盖层） |

作者用它们驱动**头发 / 裙摆 / 飘带 / 光环**这些"会自己动"的部件。
**原版 YSM 里这两层始终循环播放**，而且**各层按自己的时长独立循环**
（实测 `parallel0`=5s、`parallel4`=4s、`pre_parallel4`=8s），所以不能共用
一条时间轴。

只播单个主体动画 → 那些部件死在 rest 姿势 = 用户说的"动态模型会固定"。

新增 `ysm/clips.py::ResidentPlayer`：

```python
layer_pre(t0)    # 叠在主体动画之前
layer_post(t0)   # 叠在主体动画之后
pre_at(el) / post_at(el) / span()   # 离线采样（供量窗口尺寸用）
```

`RenderThread.run()` 的叠加顺序（后写覆盖，对齐原版）：

```
1) 程序化待机（呼吸/摆头，兜底）
2) pre_parallel 层
3) 主体动画（用户选的 / 模型默认）
4) parallel 层
5) 表情显隐
6) 视线追踪（最高优先级）
```

⚠️ `ResidentPlayer` 必须在 `PetWindow._size()` **之前**创建 —— 量比例时要把
并行层一起算进包围盒（见 §9.2）。

### 9.2 常驻默认动画 + 比例缓存修正

**常驻默认动画**：`ClipLibrary.default_clip_name()` 优先 `idle`/`default`/`stand`，
都是空壳（`length=inf`、0 骨骼，表示"保持 rest 姿势"）时**返回 None** ——
即呈现 **rest 姿势 + 并行层**，这就是原版 YSM 实体站着不动时的样子。

⚠️ **不要退回 `preview_animation`**（本模型叫 `gui`，21s/56 骨骼）。它是
**模型预览界面里的展示姿势**，带 root 位移（`MAllBody` pos y=+6/16）与放大：
实测当常驻播时人物高度从画幅 71% 涨到 **100%+ 并被裁切** —— 这正是
"桌宠过大"的来源。它仍是可播动画，用户能在轮盘/动画列表里自己选。

**缓存问题（用户："你的那一个缓存有问题"）** —— 三个原因：

1. **量包围盒时没算并行层**。并行层才是让头发飘出去的那一层，
   只量主体动画就漏掉"头发甩到最开"的瞬间 → 窗口裁到飘起的头发。
   修：`measure_ratio(..., resident=...)` 把 `pre_at/post_at` 一起合成，
   并按 `resident.span()` 单独扫 6 帧。
2. **量法版本号**。旧量法算出的比例会被一直用下去。
   修：`_RATIO_CACHE_VER`（v2 → **v3**），`_load_ratio_cache` 里
   `int(e["v"]) != _RATIO_CACHE_VER → None`（强制按新量法重测）。
3. **探针相机太近 → 动作出画 → 比例被钳成假的**。这是最隐蔽的一条：
   投影的 pb 视野**只由 zoom 决定、与探针分辨率无关**，"把方幅调大"没用。
   zoom=1.42 时实测 **8 帧出画**，包围盒被钳到画幅边缘，方幅下比例必然
   趋近 1.0 —— 量出来的是 0.9577 这个**假值**。
   修：探针改用 `probe_zoom = max(zoom, 3.2)`（相机拉远）。比例是
   **尺度无关**的，拉远不影响结果，只保证不钳；同时若仍有出画会打印警告。

**实测（亚托莉，`scripts/_remeasure.py --clear`）**：

| 量法 | 比例 | 窗口（BASE_H=340, PAD=1.25） | 出画帧 |
|---|---|---|---|
| 不含并行层 | 0.5621 | 239×340 | — |
| v2：含并行层但探针 zoom=1.42 | 0.9577（钳过） | 407×340 | **8** |
| **v3：含并行层 + 探针拉远** | **0.7101** | **302×340** | **0** |

常驻姿势实测：高 **71%**（= 1/zoom，符合设计）、宽 42~49%，**无裁切**。

> 顺带：`os.remove` 清缓存会被沙箱的 safe-delete shim 拒（`SHFileOperationW
> 失败 0x2`）。清缓存就**覆写成 `{}`**，或者靠版本号自动失效。

### 9.2b 「朝向」必须绕模型纵轴转（不能平移 pctr）

用户原话："朝向的水平设置有问题，原本理应是以模型纵轴旋转的，现在是以一个
莫名其妙的外纵轴旋转。"

根因：`measure_ratio` 为了"把人物摆到窗口正中"，把全局包围盒中心的偏移
加到了 **`pctr`** 上：

```python
self.pctr = [pctr[0] + dx, pctr[1] + dy, pctr[2]]   # ✗
```

而 `pctr` 是 `computeViewMatrixFromYawPitchRoll` 的**相机绕转枢轴**。更糟的是
`pctr` 的分量是 **pb 空间**的，pb_x/pb_y 是**地面平面**的两个轴（pb_z 才是竖向），
所以"屏幕纵向偏移 dy"被写进了一个水平轴 —— 枢轴被推离模型纵轴，
一改 yaw 模型就绕着那根外来的竖轴**甩**。

修：**绝不平移 pctr**。枢轴始终留在模型纵轴上（模型本来就由 `ctr`
＝模型包围盒中心居中，`__init__` 算出的 `pctr` 已经是模型 pb 包围盒中心）。
那段居中校正直接删掉，`dx = dy = 0`。

新增 `scripts/_test_yaw_axis.py` 专项量化：yaw 扫一圈，统计画面里
**轮廓中心的漂移量**。

| 场景 | 横向漂移 | 占窗宽 |
|---|---|---|
| 枢轴在模型纵轴上（修好后） | 7.6 px | **2.5%** |
| 枢轴被推偏 0.3 pb（复现旧 bug） | 67.9 px | **22.5%** |

判据：< 8% 窗宽算通过，同时要求"注入偏移"能明显放大该指标（否则说明
指标测不出问题）。

**另一个缓存回读 bug**：`_ratio_base_pctr` 原来只在 `measure_ratio` 的
"实测分支"里赋值，而缓存命中时**直接 return**，从没走到那一步 →
缓存里的 `dx/dy` 居中偏移**永远应用不上**（"首启准、次启偏"）。
修：在 `__init__` 里就初始化为静态 pctr。
（v3 起 dx/dy 恒为 0，这个 bug 在语义上已经消失。）
新增 `scripts/_test_ratio_cache.py` 验证「实测 ↔ 缓存」的 ratio 与 pctr 一致。

### 9.3 视线正面补偿（"绑定写反"的真正原因）
先把符号**实测钉死**（`scripts/_shot_head_rot.py` / `_probe_camera.py`）：

| 操作 | 结果 |
|---|---|
| `ry=+45` | **正脸朝向镜头** |
| `ry=-45` | 后脑勺 |
| `rx>0` | **低头**（头发盖脸） |
| `rx<0` | 抬头 |

对照 `_euler_rot`（`R = Rz·Ry(-ry)·Rx(-rx)`）：正面 = 模型 **−Z**，
纯 `ry` 时朝向 `(sin ry, 0, −cos ry)` → `ry>0` 朝屏幕右 ✓；纯 `rx` 时朝向
`(0, −sin rx, −cos rx)` → `rx>0` 低头 ✓。**原实现的符号本来就是对的。**

**真正的问题是没有中位补偿。** 从视图矩阵精确解出相机位置
（`scripts/_probe_camera.py`）：相机 yaw=ψ 时落在模型方向 `(cos ψ, 0, −sin ψ)`，
而模型正面是 −Z → **ψ=90° 才正对镜头**。桌宠相机 ψ=28°，
所以人物正面**离镜头 62°**：

* 光标在正中 → 头仍偏 62°（看着像"没在看光标"）；
* 光标在右 → 最多把头顶到正脸（Δ46°），**永远到不了右侧**；
* 光标在左 → 直接扭到后脑勺。
  → 左右极不对称，用户看到的就是"绑定写反了"。

修法（`gaze._aim`）：

```
neutral = front_yaw - cam_yaw        # 让「光标在正中」时头正对镜头
yaw     = neutral + nx * max_yaw     # 左右对称摆幅
pitch   = ny * max_pitch             # 光标在上 → ny<0 → 抬头
```

实测：`cam_yaw=28, front_yaw=90 → neutral=62°`，渲染出来**正好是正脸** ✓。
幅度也从 `nx·cos(28°)·62`（≈45°）改成 `nx·48`，左右对称。

**`front_yaw` 自动推断**：眼睛长在脸前方，所以「眼骨骼相对头骨骼 pivot 的
水平向量」就指向正面；令它等于相机方向 `(cos ψ, 0, −sin ψ)` 得
`ψ = atan2(−hz, hx)`。实测亚托莉 **89.4°**、爱恩 **89.8°**，与兜底值 90 吻合 ——
**换模型不用手调**（这直接对应"有一些局部模型会绑定反"）。推不出来时退回 90，
设置面板里也能手动指定（默认勾选"自动"）。

新增脚本：`scripts/_calib_cam_yaw.py`（看哪个相机 yaw 露正脸）、
`scripts/_probe_camera.py`（精确解相机在模型空间的方向/屏幕右/屏幕上）、
`scripts/_test_gaze_e2e.py`（光标四方向 → 真实管线 → 出图对照）。

## 10. 2026-10-05 四轮：鼠标穿透的「关闭出口」

### 10.1 问题：穿透把开关自己锁死了

`toggle_click_through()` 给桌宠窗口加 `WindowTransparentForInput`，于是桌宠
**收不到任何鼠标事件** —— 右键菜单点不出来。原来的关闭路径只有两条：

1. 桌宠右键菜单的「鼠标穿透」→ **穿透开启后根本点不到**，是单向门；
2. 托盘图标 → 设置… → 取消勾选 → 可用，但要开面板，且 Win11 默认把托盘
   图标折叠进「隐藏的图标」，用户经常找不到。

结论：**「退出设置页之后怎么关」在原实现里是没有明确答案的**，这是真缺陷。

### 10.2 修法：三个出口 + 一个系统级热键

| 出口 | 位置 | 特点 |
|---|---|---|
| 设置面板复选框 | 设置 → 窗口 → 「鼠标穿透」 | 原路径，保留 |
| **托盘菜单项**（新增） | 托盘图标 → 右键 → 「鼠标穿透」 | 图形化、一步直达；托盘是独立窗口，不受穿透影响 |
| **全局热键 Ctrl+Alt+P**（新增） | `GlobalHotkey` | 无论焦点在哪、托盘在不在都能按 |

配套：

* `_sync_click_through()` 把状态同步到**右键菜单 + 托盘菜单 + 托盘 tooltip**
  三处（tooltip 会变成「YSM 桌宠（鼠标穿透中：Ctrl+Alt+P 或托盘菜单可关闭）」，
  鼠标悬停托盘就能看到怎么关）；
* 设置页复选框下方直接写出三种关闭方式；
* 两个菜单项的 tooltip 也写明关闭方法。

### 10.3 热键的两个坑（都踩过并规避）

1. **不能挂在桌宠 HWND 上**：`toggle_click_through()` 里的 `setWindowFlags()`
   在 Windows 上会**销毁并重建原生窗口**，热键跟着失效 —— 表现就是
   "开一次穿透后 Ctrl+Alt+P 就再也没反应"。改成注册在一个**专属的、永不
   `show()` 的宿主窗口**（`WA_DontShowOnScreen` + `winId()`）上，HWND 恒定。
   `RegisterHotKey` 失败时退回到 `hwnd=0` 的线程级注册。
2. **必须显式声明 ctypes 签名**：`RegisterHotKey` 的 HANDLE 参数在 64 位下
   是指针，不设 `argtypes` 可能被截断。已在 `__init__` 里设好
   `argtypes` / `restype`。

另外 `quit()` / `closeEvent()` 里会 `removeNativeEventFilter` +
`UnregisterHotKey`，避免退出后残留全局热键。

### 10.4 验证

`scripts/_test_click_through.py`（21 项断言，全绿）。关键点是**真的投递一个
`WM_HOTKEY`**（`PostMessageW` 给宿主窗口）走完整 Qt 消息泵，而不是只调
`toggle_click_through()` 自欺欺人 —— 这样才验证得到
`nativeEventFilter` 这条链真的通。

`scripts/_shot_thru_page.py` 出图确认设置页文案不溢出，且**开着穿透时设置
面板照样可见可操作**（穿透只作用在桌宠窗口上）。

## 11. 2026-10-05 五轮：视线左右反 + 设置页「当前模型」占位符

### 11.1 视线绑定的左右反了

**现象**：光标往屏幕右，桌宠的脸却往左转（与 `_test_gaze_e2e.py` 出图一致：
第一格 `cursor:RIGHT` 脸朝左、第二格 `cursor:LEFT` 脸朝右）。

**根因（双重）**：
1. `_aim()` 用的是 `yaw = neutral + nx*max_yaw`（加号）。
2. 这个加号来自一个**错误的方向结论**：`gaze.py` 文件头原写
   "ry 为正 → 头朝屏幕右侧转"。这个结论当年来自 `scripts/_probe_gaze_sign.py`
   的判据——而它用**整幅轮廓的质心 x 位移**判断 ry 方向。
   **身体 / 头发 / 裙摆都不跟着头转**，头部信号被稀释到只剩 2~7 px，
   方向被噪声定反了。

**正确方向（几何推导 + 实测）**：
头绕竖直轴转 ry 后，正面朝向（模型空间）`P(ry) = (sin ry, 0, -cos ry)`；
屏幕右方向（模型空间）是 `R = (-sin ψ, 0, -cos ψ)`（`_probe_camera.py` 精确解，
yaw=28 时实测 `(-0.469, 0, -0.883)`）。

    脸的屏幕水平分量 = P·R = cos(ry + ψ)

中位处 `ry + ψ = front_yaw ≈ 90°`，`d(P·R)/d(ry) = -sin(front_yaw) < 0`
—— **ry 越大，脸越往屏幕左**。所以「光标在右」必须**减小** ry。

**修法**：
* `gaze.py` 新增 `yaw_side_sign()`（返回 -1/+1，由 `sin(front_yaw)` 的符号定），
  `_aim()` 改用 `yaw = neutral_yaw() + yaw_side_sign() * nx * max_yaw`；
* 把推导整个写进 `gaze.py` 文件头注释，并把 `_probe_gaze_sign.py` 的判据
  改成**几何法**（"脸的屏幕水平分量"），它现在输出正确结论
  "ry 越大 → 分量 -0.8292（头朝屏幕左）"。

**验证**：`scripts/_test_gaze_dir.py`（几何判据，不再依赖像素统计）：
光标在右 → 脸屏幕水平分量 **+0.7431**、光标在左 → **-0.7431**、正中 → 0，
左右对称；末了还出 `outputs/gaze_dir/gaze_dir.png` 供人眼复核。`_test_gaze_e2e.py`
和 `_test_pet_features.py` 的判据同步翻转为「光标在右 → yaw < 中位」。

## 13. 2026-10-05 七轮（续）：穿模后贴图消失 bug（近平面裁剪）

### 13.1 现象
模型某部分被推过相机近平面（`near=0.05`）时，整帧贴图乱掉 / 直接消失。
触发条件：前表面顶点到相机距离 `< 0.05`，即 `clip.w = -z_view ∈ (0, 0.05)`。

### 13.2 根因（在 `native/raster.cpp` 的 `ysm_render`）
原投影段对四边形 4 个顶点直接做透视除法 `iw = 1/cw` 后投影，**没有近平面
保护**。当 `cw → 0`（顶点逼近近平面）甚至 `cw < 0`（顶点已到相机背后）时，
`iw` 变负 / 趋于无穷，该顶点投影成全屏范围内的垃圾坐标，连同另外 3 个正常
顶点构成一个**覆盖全屏的退化三角形**，整帧被毁（乱掉 / 被垃圾 UV 覆盖 / 或消失）。

### 13.3 修法：裁剪空间 Sutherland-Hodgman 近平面裁剪
在投影之前，先在**裁剪空间**把四边形按半平面 `cw >= NEAR (0.05)` 裁剪：
- 逐边 `(k → k+1)` 判断 `dA = cw[k]-NEAR`、`dB = cw[k2]-NEAR`；
- `dA >= 0` 保留起点；`dA`、`dB` 异号则在交点线性插值（顶点位置 + UV）；
- `np < 3` 直接跳过（整面在近平面之后，不画）；
- 否则对裁剪后的多边形（≤8 顶点）做透视除法 + fan 三角化 `(0, i, i+1)`。

关键性质：**正常情况下没有顶点跨近平面 → 裁剪是 no-op**，四边形仍拆
`(0,1,2)+(0,2,3)`，与修复前逐像素完全一致（见 13.5）。

### 13.4 部署
- 旧 `raster.dll` 被运行中的桌宠进程（PID 848，managed `pythonw`）锁住，
  无法覆盖 → 先 `taskkill /PID 848 /F` 释放锁，再 `cp raster_new.dll raster.dll`。
- 旧版已备份为 `native/raster_old.dll`；临时 `raster_new.dll` 删除。
- 用 `scripts/build_native.py --force --only raster.dll` 从（已修的）
  源重编，产物 127620 B 与手工部署一致，冒烟 `raster_faces` 通过。
- 重新启动桌宠即加载修复版（DLL 仅在启动时加载一次）。

### 13.5 验证（`scripts/_verify_clip_fix.py` + `verify_cpp.py`）
- **无回归**：正常 zoom（0.6/1.0/1.42/2.5）× OLD vs NEW 逐像素差 = **0**。

## 14. 2026-10-05 八轮：贴图消失真因（ONCE 末帧钳死）/ 朝向默认 90° / 清理缓存

### 14.1 「穿模后贴图渲染直接消失」——真因是动画末帧被永久钉住

**定位过程**（重要教训）：先怀疑了 C++ 光栅的**近平面**（模型穿到相机
`near=0.05` 之内 → 透视除法 `iw=1/cw` 负/无穷 → 全屏退化三角形），并做了
§13 的裁剪修复。但用户重启后**依旧复现** → 说明那不是触发路径。

改用「穷举输入」法定位：逐个渲染模型**全部 90 余个动画片段**（`_diag_clips.py`），
按覆盖掉到 <2% 报警 → 命中 **`death`**（覆盖 16.2% → **0.0%**）。再逐骨骼查
姿态矩阵，得到决定性证据（`_diag_death.py`）：

| t | 覆盖 | `det` 下界 | 骨骼平移范围 |
|---|---|---|---|
| 0.00 | 16.2% | 1.00 | x[-1.0,0.4] z[-1.5,0.3] |
| 0.17 | 1.8% | 0.04 | x[-0.3,0.1] z[-0.5,0.1] |
| 0.25~0.92 | **0.0%** | **0.00** | **x[0,0] z[0,0]** |

`det=0`（旋转矩阵奇异）+ 所有骨骼平移在 x/z 上塌成 0 → **每副三角形都退化成
零面积** → 什么都不画 → 纹理消失。

根因在 `src/ysm/clips.py::ClipPlayer.tick()`：ONCE 动画播完时**只置了
`_done=True`，却仍每帧 `return c.sample(t=length)`** —— 末帧姿势被**永久**叠在
待机之上。而 `extra0~4` / `death` 这类动画的末帧正是「整副骨骼 scale=0」的隐藏帧
（原始数据里 `CBB2` 等骨骼 `scale.post=[0,0,0]`）。**动画一播完，桌宠就永久隐形**。
本类 docstring 早就写着「播放结束后自动回到待机」，实现却没做到。

修法（`tick()`）：ONCE 超时后 `_done=True` 并**立即 `return {}`**，把叠加权交还
待机/常驻层；显式传 `yaw/pitch` 的调用方不受影响。

> 教训：**「输出突然消失」类问题，先穷举输入（每个动画 × 每个时间点）看哪个
> 输入让输出变空，而不是先怀疑渲染管线的数学**。近平面确实是真实缺陷（该修），
> 但它不是这个 bug 的路径——两者都要靠证据区分，不能靠「听起来合理」。

### 14.2 朝向：默认 yaw=90 / pitch=0，且**持久化**

## 15. 2026-10-05 九轮：窗口在、人不见（取景口径 + 常驻并行层两处真因）

### 15.1 现象

用户报「模型导入进去但显示不出来，窗口是竖长方形但没内容」（`慧慧1.2版本.ysm`）。
进程活着、窗口 173×323 正常、日志无异常，但离屏冒烟覆盖率只有 **1.0%**
（对照健康模型 9.6%~20.5%）。

### 15.2 三处真因（按发现顺序）

1. **包围球被远端特效面撑大 10 倍**。`FastRenderer.__init__` 原来用全体可见面顶点
   算 `ctr/radius`，而慧慧的 `ysmGlow_*` 特效面在 `z≈-26.7` 处（约 12% 顶点），
   算出来 `radius=21.13`，角色本体其实只有 1.8×2.5 → 相机距离
   `radius/tan(fov/2)≈82`，人物缩成几个像素。
   修法：新增模块级 `_frame_core(vis_v, gap=3.0, trim=2.5)` —— 以顶点中位数为心算
   距离 `d`，`p99 > 3.0×p75` 时只保留 `d <= 2.5×p75` 的顶点取景，被裁比例记在
   `self.frame_trim`。健康模型（斯卡蒂 p99/q75=2.2、芙宁娜≈2.8、atri≈1.6）不受影响。
   慧慧 `radius 21.13 → 4.48`。
2. **相机距离该用「模型高度」而不是半径**。`radius` 把横向张开（手臂/头发/裙摆）
   也算进去，实测 200×300 里人物只占高 ~25%，而代码注释声称 zoom 1.42 → 73%。
   修法：按 `src/phys/bind.py` 的 `P_MAT = [[0,0,-1],[-1,0,0],[0,1,0]]`
   （`pb_x=-model_z`、`pb_y=-model_x`、`pb_z=model_y`，pb 的 Z 是屏幕竖直）把核心顶点
   转到 pb，新增 `self.frame_r = (lo[:,2].max()-lo[:,2].min())/2`；四处相机距离
   `dist = self.radius/...` 全改成 `self.frame_r/...`（`project_point`、`measure_ratio`、
   `_render_cpp`、`_render_raw`）。占高 25% → 66~90%。
3. **常驻并行层（`pre_parallel` / `parallel`）在桌宠里必然藏身体**。运行时叠加
   `ResidentPlayer.layer_pre/layer_post` 后剪影从 200×230（76.7%）掉到 18×77（25.7%），
   只剩一个头。逐层实测 `pre_parallel0`（`len=0`，static）单独就能复现；pre 合成里

### 15.3 上游证据（为什么这些层在桌宠里必然出错）

- `ParallelProcessor`（CFR 反编译 `temp/cfr/src2/.../client/model/processor/ParallelProcessor.java`）：
  槽位匹配 `^<prefix>.<slotName>_[0-7]$`、动画名 `^<slotName>[0-7]$`；
  `NamedAnimationPredicate:27-29` 直接 `playLoopAnimation` → 游戏里 `pre_parallel<N>`
  也是**无条件循环**播放。
- 这些层的键帧是 **molang 表达式**：慧慧 pre 层出现 `!v.roaming.p`、`ysm.has_helmet`、
  `v.arrow_1>0`、`ysm.armor_value`、`q.remaining_durability(...)`。桌宠里没有游戏内变量，
  静态解析把 `!v.roaming.p` 当 0 → scale 0 → 身体消失。
- **决定**：不改「scale=0 隐藏子树」的语义（那是原版行为，本机无法与游戏对照验证），
  改为**默认关闭常驻并行层**，保留设置项供用户手动开。

## 16. 2026-10-05 十轮：「人物、特效叠在一起，看不清」→ 清晰模式（只画人物本体）

### 16.1 现象与用户原话

用户（m06988，原话）：

> 为什么多数模型部件都渲染了，导致任务（人物），特效叠在一起，看不清

即：桌宠窗口里能看出人，但**人和一大堆不该出现在静止状态的东西画在同一层**，
越看越花。§15 修好的是「窗口在、人不见」，这一轮修的是「人出来了，但糊在一起」。

### 16.2 取证：模型里到底有什么

以用户正在用的 `慧慧1.2版本.ysm`（骨骼 968 / 面 24098，贴图 3500×3500 内嵌
rawRGBA「周年服饰」）为例，按**根骨骼**统计面数：

| 根骨骼 | 骨骼 | 面 | 说明 |
| --- | ---: | ---: | --- |
| `girl` | 758 | **13932** | **人物本体**（y −0.26..3.33，含 `Head`） |
| `texiao` | — | 5642 | 特效（y −2.45..6.03，含 26 单位外的刀光/法阵） |
| `DAZ` | — | 2016 | 平面立绘（z 跨度仅 0.06，纯平片） |
| `MZ2` | — | 1926 | 部件 |
| `tx` | — | 420 | 部件 |
| `bone358` | 2 | 96 | 正贴人物中心的一块大面（8.67×8.47×2.56 单位） |
| `bone480` | — | 66 | 部件 |

⇒ **人本体只占 57.8% 的面，另外 42% 是特效 / 立绘 / 游戏内 UI 部件**。
顶点跨度最大的 12 根骨骼**全是特效**：6× `ysmGlow_dg1_a89..a94`（跨度 11.31×8.49×11.31，
中心 (0, 1.35, **−26.31**)）、`D9/D10/D11`（8×0×8，z=−26.31）、`ysmGlow_pd54/55`
（8×0×8，中心 (4, 2.19, 4)）、`bone358`（中心 (0.1, 1.51, 0.05)）。

跨模型看，这些额外根的名字本身就是证据 —— 斯卡蒂/铃兰里它们直接叫
**`MUI` / `BeiJing` / `MZhuanPan` / `MTouzi`**（游戏内 UI：面板 / 背景板 / 转盘 / 骰子）。
苏沐星的 `Gui` 只有 **10 个面**，却是一整块背景板，占掉 19% 画幅。

模型作者是怎么藏这些东西的：靠它自带的 `pre_parallel*` **常驻并行层**，
在静止状态下用 `scale=0` 把它们关掉。慧慧的该层里 `scale=[0,0,0]` 的骨骼 58+ 根，
整层算下来 **`vis=False` 的面 = 11588 / 24098（48%）**。
桌宠没有游戏那套 molang/状态机（§15.3），所以：

- **常驻层关（当时默认）** → 作者想藏的部件**全被画出来**，糊在人物上（用户看到的现象）；
- **常驻层开** → 该层会顺带把**人物本体也压成一小团**（可见面只剩约 3.6 单位高）。

### 16.3 更正：`bone358` 不是身体的父节点（§15.2 旧结论错）

§15.2 第 3 条当时写「`bone358` 是整个可见身体的父节点，放开它就回到 76.7%」。
本轮用同一 renderer、同一相机重跑三态：

| 状态 | 剪影 |
| --- | --- |
| `pre` 层 | 44×93 px（1817） |
| `pre` 层 + `bone358 scale=[1,1,1]` | 191×230 px（35467） |
| `pre` 层 + **不画** `bone358` | **仍是 44×93 px（1817）** |

⇒ `bone358` 与「身体是否可见」无关；它只是**自己那 96 个面很大**（用 `fr.parent`
展开子树只有 `bone358` + `bone512` 两根骨骼）。`girl` 的祖先链是
`Head <- AllHead <- bodyon <- body <- UpBody <- MUpBody <- AllBody <- AllBodyD <- MAllbody
<- Root <- girl`，与 `bone358` 毫无关系。「常驻层开着人变小」的真机制是
**整层应用后可见面集合只剩 y ∈ −0.20..3.36 的一小团**（分 10 层统计可见面得出）。
「默认关闭常驻并行层」这个决定本身仍然成立。

### 16.4 三个候选修法的定量判决

都会重新取景，不固定就会把镜头变化当成画面变化（早期 probe25 的「斯卡蒂 C 覆盖率
反升」就是这么来的）—— 现在会把参考实例的 `ctr/pctr/radius/frame_r/aspect/
bbox_lo/bbox_hi/screen_w/screen_h/frame_trim` 复制给每个变体。
